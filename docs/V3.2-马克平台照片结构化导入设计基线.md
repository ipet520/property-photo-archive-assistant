# V3.2 设计基线 v1.1

## 马克开放平台照片结构化导入版

状态：第一、二、三阶段已封版；第四阶段第一刀已封版，第二刀批次协调底座开发中。

## 1. 总体架构

```text
马克 API 查询
→ 用户勾选照片
→ 主进程事务式下载
→ 保存来源清单与结构化数据
→ 生成工作台导入包
→ 追加并去重进入现有工作台
→ 人工确认
→ 复用现有预览、归档和台账流程
```

核心原则：新增照片来源，不新建平行归档系统。

马克照片默认使用平台结构化字段。本地照片继续使用 OCR；马克照片仅在用户主动选择时使用 OCR 或 AI 作为异常补充。

## 2. 安全与存储边界

- 组织 KEY 只在 Electron 主进程使用。
- 使用 Electron `safeStorage` 加密后保存到 `userData`。
- 前端只能读取是否已配置、组织 ID、更新时间和连接状态。
- KEY 不得进入设置导出、备份、日志、错误详情、前端草稿或 IPC 返回值。
- 签名计算和 API 请求统一在主进程执行。
- 便携版移动到其他 Windows 用户或设备后，应要求重新输入 KEY。

正式下载目录：

```text
文档\物业工作照片归档助手\marki-import\
  <orgId>\
    <teamId>\
      <拍摄日期>\
        <momentId>.jpg
```

来源清单与正式照片使用同一套文档数据根目录：

```text
文档\物业工作照片归档助手\marki-import\
  <orgId>\
    source-manifest.json
```

- 生产调用由 Electron 主进程传入 `app.getPath('documents')`，或传入由现有 `settingsService` 确定的文档数据根目录。
- 来源清单服务保留 `documentsPath` 参数，便于自检传入系统临时目录。
- `.runtime` 只用于开发测试，不得作为正式来源清单或业务照片目录。
- `userData` 只保存安全凭证等内部配置，不得将正式照片和来源清单迁移到 `userData`。

## 3. 来源标识与去重

```text
sourceType = marki_api
sourceKey = marki_api:<orgId>:<momentId>
```

同一 `sourceKey` 不重复下载、不重复创建照片对象、不重复进入工作台。

现有照片对象只增加：

```text
sourceType
sourceKey
sourceMetadataRef
capturedAt
```

完整接口明细由主进程保存，前端照片对象继续使用现有的 `originalPath`、`originalName` 和 `previewUrl`。

## 4. 字段映射

| 软件字段 | 马克来源 | 规则 |
| --- | --- | --- |
| 日期 | 日期 → 时间 → postTime | 水印拍摄时间优先，上传时间只兜底 |
| 项目 | 小区名称 | 匹配现有项目或别名，未匹配时要求确认 |
| 归档分类 | markName | 匹配现有分类或映射规则，未匹配时保留候选 |
| 工作内容 | 工作内容 → 标题 | 过滤占位值 |
| 位置/区域 | 地点 → 有效经纬度 | 经度或纬度为零时保持为空，由归档层按现有规则显示“现场” |
| 拍照人员 | 上传人 | 查询和来源追踪使用，同时保留 uid |
| 备注 | 工作备注 | 无有效内容时不生成空字段 |
| 来源追踪 | id、teamId、防伪码 | 保存到主进程来源明细 |

机动车水印的工作内容采用：

```text
违停类型 + 车牌号
```

## 5. 字段清洗

以下值视为空：

```text
请输入……
请选择……
未填写
暂无
空字符串
纯空格
模板默认占位值
```

处理顺序：

```text
解析 content
→ 规范字段名
→ 清洗字段值
→ 过滤占位内容
→ 执行映射
→ 生成候选归档建议
```

## 6. 事务式下载

```text
建立 downloading 来源记录
→ 下载到 <momentId>.jpg.part
→ 校验 HTTP 状态
→ 校验文件非空
→ 校验 JPEG 文件头
→ 校验图片宽高
→ 原子改名为 <momentId>.jpg
→ 写入来源清单
→ 标记 imported
→ 生成工作台导入包
```

下载、写盘、校验或原子改名失败时记录明确原因并标记 `download_failed`，允许重试。正式 JPG 完成后的来源清单提交失败按第二刀恢复规则处理，不得误记为普通下载失败。未完成最终改名和来源清单写入前，不得进入工作台。

## 7. 工作台导入包

```javascript
{
  batchId,
  photos,
  recognitionResultsByPhoto,
  watermarkRecordsByPhoto,
  archiveSuggestionsByPhoto
}
```

马克结构化识别结果：

```text

```

识别成功不等于已整理、已确认或已归档，仍须进入现有人工确认链路。

## 10. 阶段验收与下一阶段边界

V3.2 第一阶段“马克平台 API 基础能力”已经人工验证通过并封版：

```text
组织 KEY 安全加密保存
连接测试正常
团队列表正常
成员分页正常
KEY 不回显、不进日志
团队不自动选中
成员电话不进入前端
重启后配置可继续使用
```

第二阶段范围冻结为：

```text
来源清单
→ sourceKey 去重
→ downloading 状态
→ .part 事务下载
→ 文件头、大小和宽高校验
→ 原子改名
→ imported / download_failed 状态
→ 下载失败重试
```

第二阶段不得接入工作台，不做字段映射，不修改现有归档流程。

### 第二阶段第一刀

第一刀只建立来源清单与去重底座：

```text
sourceKey = marki_api:<orgId>:<momentId>
来源记录持久化
importStatus = discovered
按 sourceKey 查询是否存在
批量去重判断
```

来源清单按组织保存：

```text
marki-import\<orgId>\source-manifest.json
```

写入要求：

- 相同 `sourceKey` 幂等更新，不重复创建记录。
- 使用进程内写入队列避免并发覆盖。
- 先写临时文件并同步到磁盘，再原子替换正式清单。
- 清单损坏时停止写入，不得静默覆盖为空清单。
- 第一刀只保存来源身份摘要，不保存完整远程 URL、原始 content 或组织 KEY。
- 第一刀允许的 `importStatus` 只有 `discovered`。
- 第一刀读取清单时遇到 `downloading`、`imported`、`download_failed` 或其他未知状态，必须按损坏清单保护逻辑拒绝读取，不得静默改写为 `discovered`。
- `downloading`、`imported`、`download_failed` 在第二刀实现事务下载时再正式加入状态集合。

第一刀不下载照片，不新增页面，不接工作台，不做字段映射，不修改归档和台账服务。

### 第二阶段第二刀

第二刀在来源清单底座上加入事务式 JPG 下载：

```text
discovered / download_failed / 中断的 downloading
→ downloading
→ 下载到 <momentId>.jpg.part
→ 校验 HTTP 状态
→ 校验文件非空和大小上限
→ 校验 JPEG 文件头
→ 解析并校验图片宽高
→ 原子改名为 <momentId>.jpg
→ imported
```

状态规则：

- `discovered` 只能进入 `downloading`。
- `download_failed` 可以重新进入 `downloading`。
- 中断遗留的 `downloading` 可以重新开始下载，并累计尝试次数。
- `downloading` 在下载、写盘、校验或原子改名失败后进入 `download_failed`；正式 JPG 完成后的清单提交失败保持 `downloading`，等待重试补记。
- `imported` 不允许重新进入下载状态；同一 `sourceKey` 再次请求时直接返回已导入结果。
- 未知状态继续按损坏清单保护逻辑拒绝，不得静默改写。

文件与安全规则：

- 正式路径保持为 `文档\物业工作照片归档助手\marki-import\<orgId>\<teamId>\<拍摄日期>\<momentId>.jpg`。
- `.part` 与正式 JPG 位于同一目录，只有通过全部校验后才执行原子改名。
- 下载失败时清理 `.part`，保留来源记录、受控错误码、短错误信息和尝试次数，允许用户重试。
- 来源清单只保存相对文件路径、文件名、大小、宽高、SHA-256 和完成时间。
- 完整远程 URL 只在单次下载期间存在于主进程内存，不写入来源清单、日志或错误信息。
- 下载请求使用手工重定向，每一跳都在发出下一次请求前解析并校验协议，只允许 HTTPS。
- 最多允许五次重定向；超过次数、缺少 `Location`、地址无法解析或协议不是 HTTPS 时返回受控错误，错误摘要不得包含重定向地址。
- HTTPS 跨主机重定向允许继续，但每一跳都必须重新校验。
- 不覆盖目标位置中无法通过校验的既有文件。

正式 JPG 与来源清单属于两个独立文件，无法形成跨文件原子事务。恢复规则冻结为：

- 正式 JPG 原子改名完成后，再提交来源清单的 `imported` 状态。
- 如果正式 JPG 已完成但 `imported` 清单提交失败，保留正式 JPG 和原 `downloading` 状态，不得误记为普通 `download_failed`。
- 对外只返回 `marki_manifest_commit_failed` 和固定安全消息，不暴露原始文件系统异常、完整路径或远程 URL。
- 下次重试优先检查正式 JPG；校验通过时不再请求网络，直接补记 `imported`。
- 补记仍失败时继续保留正式 JPG，并再次返回受控清单提交错误。
- 正式 JPG 存在但校验失败时继续执行 `target_file_conflict` 保护，不覆盖、不删除。

第二刀仍不接页面和工作台，不做字段映射，不修改归档、Excel 台账或本地 OCR 流程，不处理视频，也不自动删除来源照片。

### 第三阶段：结构化数据转换

第三阶段只建立主进程后端的数据转换能力：

```text
马克 content
→ 解析字段对
→ 规范字段名
→ 清洗占位值
→ 日期、项目、分类和工作内容映射
→ 生成 recognitionResultsByPhoto
→ 生成 watermarkRecordsByPhoto
→ 生成 archiveSuggestionsByPhoto
→ 组装工作台导入包
```

本阶段输入为马克照片 API 记录、第二阶段已完成的 `imported` 下载结果和当前项目/分类配置。只有 `momentType = 1` 且已完成事务式下载的 JPG 可以生成导入包。

字段清洗规则：

- 支持马克 `content` 的 JSON 字符串、字段对数组和普通字段对象。
- `拍摄日期`、`拍照日期` 统一为 `日期`；`拍摄时间`、`拍照时间` 统一为 `时间`。
- `项目`、`项目名称`、`小区` 统一为 `小区名称`。
- `地址`、`位置`、`客户位置`、`发现地点` 统一为 `地点`。
- `请输入...`、`请选择...`、`请填写...`、`未填写`、`未设置`、`暂无`、`null`、`undefined`、横线、空字符串和纯空格在映射前过滤。
- `null` 和 `undefined` 按完整值不区分大小写过滤；数字 `0`、字符串 `0` 和正常包含“无”的业务文本不得误删。
- 字段容器使用无原型对象，`__proto__`、`prototype`、`constructor` 在键名基本清洗后显式拒绝。
- 同一字段出现多个不同有效值时保留首个值，并生成待核对提示。
- `content` 解析失败不得阻止照片进入工作台导入包，但识别结果标记为结构化数据异常，并要求手工补充或由用户主动选择 OCR。

日期与位置规则：

```text
日期字段中的日期
→ 时间字段中的日期
→ postTime 的东八区日期
```

- 日期或时间字段中包含实际拍摄时间时，生成东八区 `capturedAt`。
- 水印只有时分秒而没有日期时，以 `postTime` 的东八区日期补足日期，但保留水印实际时间。
- 使用 `postTime` 兜底时必须生成提示，且不得把它伪装成水印实际日期。
- `地点` 优先于经纬度；没有地点时，有效经纬度可以形成辅助位置。
- 经度和纬度必须同时为有限数字、位于合法范围且均不等于 `0`，才可形成辅助位置。
- `(0, 0)`、`(0, lat)`、`(lng, 0)`、越界值和非有限数字均属于合法空位置，不报错，也不在映射层写入“现场”。

项目和分类匹配规则：

- 项目只按现有项目名称、项目配置中的别名或调用方提供的明确别名表匹配。
- 分类只按现有分类名称、分类配置中的别名或明确的水印名称映射表匹配。
- `时间地点（兜底选择）` 明确映射到现有的 `时间地点水印` 分类。
- 未匹配项目或分类时只保留候选值，必须由用户确认，不自动创建配置，也不静默写入现有表单值。
- 不把“其他”作为未知项目或未知分类的自动兜底。
- 归档建议必填项固定为日期、项目、归档分类、工作内容四项；任一项缺失或未匹配时状态为 `needs_completion`。

工作内容规则：

- 普通水印按 `工作内容 → 标题` 生成工作内容。
- 机动车水印按 `违停类型｜车牌号` 组合工作内容。
- 标题、施工单位、违停类型和车牌号可形成辅助关键词。
- 防伪码只属于来源追踪信息，不进入工作台导入包的关键词、备注或识别原文。

来源元数据引用固定为：

```text
marki_source_metadata:<orgId>:<momentId>
```

来源元数据正式路径固定为：

```text
文档\物业工作照片归档助手\marki-import\
  <orgId>\
    source-metadata\
      <momentId>.json
```

来源元数据只允许保存：

```text
schemaVersion
sourceMetadataRef
sourceKey
sourceType
orgId
momentId
teamId
uid
postTime
capturedAt
markName
antiCounterfeitCode
parsedEntries
createdAt
updatedAt
```

- `antiCounterfeitCode` 保存清洗后的防伪码，来源元数据服务必须自行再次过滤空值、横线、未填写、未设置、暂无、`null` 和 `undefined` 等占位内容。
- `parsedEntries` 使用 `{ key, value }` 数组保存清洗后的合法原始条目，保留输入顺序及重复字段关系；特殊键、占位值、对象值和不可序列化值不得进入该数组。
- 转换过程可以使用无原型 `fields` 映射并按首个有效值生成业务建议，但 `fields` 和临时 `parsedFields` 不属于来源元数据正式白名单。
- 不保存组织 KEY、签名、请求头、完整远程 URL、原始 `content` 或完整 API 响应。
- 同一引用更新同一个 JSON 文件；写入采用同目录临时文件、磁盘同步和原子替换。
- 已有元数据损坏时拒绝覆盖，错误只返回受控代码和安全短消息。
- 生产调用由主进程传入 Documents 数据根目录；第三阶段只提供持久化服务，不接主进程 IPC。

工作台导入包结构保持为：

```javascript
{
  batchId,
  photos,
  recognitionResultsByPhoto,
  watermarkRecordsByPhoto,
  archiveSuggestionsByPhoto
}
```

照片对象增加并保留：

```text
sourceType = marki_api
sourceKey = marki_api:<orgId>:<momentId>
sourceMetadataRef = marki_source_metadata:<orgId>:<momentId>
capturedAt
```

- `sourceMetadataRef` 与 `sourceKey` 相互独立，指向对应的后端来源元数据记录，不向前端暴露真实存储路径。
- 照片对象使用第二阶段下载后的 `originalPath`、`originalName` 和本地 `previewUrl`。
- 同一导入包内按 `sourceKey` 去重，保留首项并在外层 bundle 返回稳定的重复项统计。
- 正式识别模型支持 `source = marki_api`、`providerType = structured_data`。
- 有效结构化数据使用现有工作台认可的成功状态 `status = recognized`；该状态不依赖 OCR 原始文本，`content` 解析失败仍使用受控失败状态。
- 无论字段是否完整，归档建议都保持 `needsHumanReview = true`，不得自动确认、自动归档或跳过现有人工确认链路。
- 远程 URL、原始 `content`、完整 API 响应、防伪码、组织 KEY 和签名信息不得进入工作台导入包。

转换服务同时提供纯 bundle：

```javascript
{
  workbenchImportPackage,
  sourceMetadataRecordsByRef,
  deduplication
}
```

- `workbenchImportPackage` 仍严格保持原五字段结构，不增加第六个顶层字段。
- `sourceMetadataRecordsByRef` 以 `sourceMetadataRef` 为键，每张工作台照片必须有且只有一条对应来源记录。
- `deduplication` 固定包含 `inputCount`、`uniqueCount`、`duplicateCount` 和 `skippedItems`；每个跳过项只保存 `sourceKey`、`keptInputIndex` 和 `skippedInputIndex`。
- 当前仅完成同一 bundle 内的批内去重，尚未连接正式工作台，不声称已经完成工作台已有照片的全局去重。
- 纯 bundle 只生成可 JSON 序列化的数据，不写盘、不请求网络，也不修改输入对象。
- 后续接主进程时必须按“生成 bundle → 保存全部来源元数据 → 确认全部成功 → 交付五字段工作台包”的顺序编排。
- 多条来源元数据分别写入独立 JSON 文件，不声称多个文件之间具备跨文件原子事务；中途失败时已成功文件可以幂等复用，但整批工作台包不得提前交付。

第三阶段仍不接 Electron 主进程 IPC、前端查询页面和现有工作台状态；不执行正式归档，不修改 Excel 台账，不处理视频，不自动创建项目或分类，也不修改本地 OCR 流程。

### 第四阶段第一刀：主进程编排底座

第四阶段第一刀只建立后端编排服务，不注册 IPC，不建立页面，也不把照片实际追加到工作台。公开入口固定为：

```javascript
prepareMarkiStructuredImport({
  documentsPath,
  orgId,
  items
}, options)
```

- `documentsPath` 必须由未来 Electron 主进程明确传入正式 Documents 数据根目录，服务不得回退到 `userData` 或其他默认目录。
- `orgId` 为当前马克组织 ID，`items` 为第二阶段已经完成事务式下载且状态为 `imported` 的照片记录。
- 项目和分类配置只通过 `loadConfigs(documentsPath)` 读取，不接受前端输入配置，不使用默认项目、默认分类或硬编码兜底。
- 编排服务复用 `buildMarkiStructuredImportBundle()` 生成第三阶段 bundle，并复用 `saveMarkiSourceMetadata()` 保存来源元数据，不复制字段映射、清洗、去重或持久化逻辑。

固定返回结构为：

```javascript
{
  success,
  batchId,
  inputCount,
  metadataSavedCount,
  failedCount,
  failures,
  deduplication,
  workbenchImportPackage
}
```

其中 `success = failedCount === 0`，`inputCount` 为原始输入数量。只有所有来源元数据都保存成功时，`workbenchImportPackage` 才返回第三阶段定义的五字段工作台包；任何一条来源元数据保存失败时，该字段必须为 `null`。

来源元数据按 `sourceMetadataRef` 的确定顺序逐条保存。每条记录继续使用来源元数据服务的单文件临时写入和原子替换能力；多个独立元数据文件之间不构成跨文件原子事务。单条失败时：

- 记录安全失败摘要并继续尝试后续记录。
- 已经成功保存的独立元数据文件不回滚、不删除。
- 整批工作台包暂不交付。
- 用户重试整批时复用同一 `sourceMetadataRef` 的幂等保存能力，补齐失败记录，不生成重复文件。

`failures` 每项只允许包含：

```javascript
{
  sourceMetadataRef,
  sourceKey,
  code,
  message
}
```

失败摘要不得包含 Documents 路径、本地照片路径、远程 URL、原始 `content`、`parsedEntries`、防伪码、原始异常对象、堆栈、组织 KEY 或签名信息。整批输入无效、配置读取失败或 bundle 构建失败时返回固定代码和安全短消息，不透传底层异常。

本刀不包含 Electron 主进程 IPC、preload、批次存储目录、查询或导入页面、现有工作台合并与全局去重，也不修改归档、Excel、本地 OCR、照片下载和来源清单服务。第二刀及其页面衔接能力尚未实现。

### 第四阶段第二刀：导入批次临时持久化与受控 IPC

第二刀只建立内部临时批次协调能力。批次文件固定保存在：

```text
app.getPath('userData')\marki-import-batches\<batchId>.json
```

- 批次不属于正式来源资料，不写入 Documents 下的 `marki-import`，也不写入项目源码、照片下载目录或 renderer 指定的位置。
- `userDataPath` 只由 Electron 主进程通过 `app.getPath('userData')` 提供，renderer 不得传入目录、文件名或任意文件路径。
- 每个批次文件使用同目录唯一临时文件、独占创建、写入后 `sync`、关闭文件及安全替换；失败时清理本次临时文件。
- 同一 `batchId` 的写入、查询清理和消费使用进程内串行锁。不同批次之间不构成跨文件事务。
- 已有批次 JSON 损坏时拒绝读取和覆盖，保留原文件供人工恢复。

批次状态固定为：

```text
不存在 → preparing
preparing → ready
preparing → failed
failed → preparing
ready → consumed
```

禁止 `ready` 回退到 `preparing` 或 `failed`，也禁止 `consumed` 回退到任何可交付状态。`failed → preparing` 只用于整批幂等重试，并要求输入数量和批内去重统计与原失败批次一致。

批次记录 `schemaVersion = 1`，固定保存：

```text
schemaVersion
batchId
status
inputCount
metadataSavedCount
failedCount
failures
deduplication
workbenchImportPackage
createdAt
updatedAt
expiresAt
consumedAt
```

- `batchId` 只允许字母、数字、下划线和横线，拒绝点号、路径分隔符、控制字符和路径穿越。
- `preparing` 与 `failed` 的 `workbenchImportPackage` 必须为 `null`。
- `ready` 必须保存第三阶段定义的严格五字段工作台包，包内 `batchId` 必须与批次一致，不允许第六个顶层字段。
- 工作台包深拷贝后保存和返回，批次服务不修改照片、识别结果、水印记录或归档建议的业务内容。
- `consumed` 立即清除工作台包，只保留短期防重复消费的墓碑记录。
- `failures` 继续严格使用 `sourceMetadataRef`、`sourceKey`、`code`、`message` 四字段安全白名单。
- 批次不得保存原始异常、堆栈、组织 KEY、签名、完整远程 URL、原始 `content`、`parsedEntries`、防伪码或 API 原始响应。

生命周期固定为：

```text
preparing  1 小时
ready      24 小时
failed     24 小时
consumed   10 分钟墓碑
```

过期批次清理后不得继续返回旧工作台包。时间计算由服务统一完成，自动自检可以通过 `options.now` 注入确定时间。

查询入口 `getMarkiImportBatch(userDataPath, batchId)` 不改变状态。`ready` 返回五字段工作台包；`preparing`、`failed` 和 `consumed` 只返回安全状态摘要，工作台包固定为 `null`。查询结果不包含内部批次文件路径。

消费入口 `consumeMarkiImportBatch(userDataPath, batchId)` 只允许 `ready → consumed`：

- 首次消费返回 `alreadyConsumed = false`，不返回工作台包。
- 对尚未过期的 `consumed` 墓碑重复消费时，幂等返回 `alreadyConsumed = true`。
- `preparing` 和 `failed` 不得消费。
- 并发消费通过同一批次串行锁保证只有一次真实状态转换。

Electron 主进程只注册：

```text
marki:get-import-batch
marki:consume-import-batch
```

马克联网 API 继续使用 `safeMarkiCall`，由该包装加载组织凭证后执行请求。本地批次查询和消费使用独立的 `safeMarkiLocalCall`：直接执行本地服务，不读取组织 KEY，不调用 `loadMarkiCredentials`，也不依赖 `safeStorage`。两类调用都通过 `toSafeMarkiError` 输出安全错误，不返回原始异常、堆栈或内部批次路径。

两个本地批次 IPC 仍由主进程固定传入 `app.getPath('userData')`，renderer 只能传 `batchId`。preload 接口保持 `getImportBatch(batchId)` 和 `consumeImportBatch(batchId)`，不增加路径参数或其他写入能力。

本刀不注册 `marki:prepare-structured-import`。在主进程尚未建立照片查询缓存或安全选择令牌前，不允许 renderer 传入完整 moment、远程 URL、原始 `content` 或下载结果。本刀也不建立照片查询页面，不把批次追加到现有工作台，不实现工作台 `sourceKey` 全局合并去重，不修改归档、Excel、本地 OCR 或 React 状态。后续刀次尚未实现。

## 11. 官方接口附录

### 获取组织的团队列表

- 请求方式：GET 或 POST。
- 请求地址：`https://open-api.markiapp.com/marki/org/team`。
- 业务参数：无。
- 分页：无。
- 响应列表：`data.teamOrgList`。
- 团队字段：`teamId`、`teamName`、`createUID`、`manageUIDs`、`createTime`、`parentTeam`、`OrganizeId`。

### 获取团队的成员列表

- 请求方式：GET 或 POST。
- 请求地址：`https://open-api.markiapp.com/marki/team/mem`。
- 参数：`teamId`、`next`。
- 分页：将响应的 `data.next` 原样传给下一次请求，直到 `data.hasMore` 为 `false`。
- 第一页统计：`regTotal`、`unRegTotal`、`total`。
- 响应列表：`data.memberList`。
- 成员字段：`uid`、`nickname`、`phone`、`joinTime`、`memberType`。
- 软件只向前端返回筛选需要的 `uid`、`nickname`、`joinTime` 和 `memberType`，不返回电话号码。

公共请求头、签名规则和响应状态码沿用马克开放平台 `1.API 使用` 文档。
