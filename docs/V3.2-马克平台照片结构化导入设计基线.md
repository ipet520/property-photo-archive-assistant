# V3.2 设计基线 v1.1

## 统一照片池忽略与还原状态闭环

“忽略”冻结为独立特殊状态，只暂停照片的正常处理阶段，不删除照片，也不重置智拣结果。操作只作用于当前选中的可忽略照片；已归档、正在归档和原图缺失照片不得普通忽略。

忽略照片时必须：

- 保留来源类型、来源键、来源元数据引用和本地托管原图；
- 保留 Marki 平台基线、recognition、watermark、archive suggestion 与来源感知补充层；
- 保留本地 OCR 结果、canonical 结果、人工草稿、预览和已有冲突记录；
- 保存忽略前的 `sortStatus`、`smartSortStatus`、后台识别阶段和最小分组成员前态；
- 从当前有效 `smartSortResult` membership 中移除照片，删除空分组并重算分组数和照片数；
- 清除被忽略照片的选择状态；当前照片被忽略时切换到安全后备照片；
- 完成单文件自动快照后再提交工作台状态。

还原照片时按忽略前阶段处理：

- `not_run` 或 `failed` 恢复原阶段，不恢复分组；
- `completed` 或 `needs_completion` 仅在原 `smartSortResult` 身份仍有效时恢复原 membership，不重新 OCR、不重新生成整套分组；
- 原分组结果已经失效或重建时，不挂回旧分组，安全恢复为 `not_run`，并记录 `membership_expired`；
- 已归档、正在归档或原图缺失等高优先级状态不得被普通还原覆盖；
- 已消费的忽略前态在还原成功后清除，重复忽略和重复还原保持幂等。

忽略前态只保存恢复所需的状态、分组标识、分组安全摘要和成员集合类型，不复制完整 recognition、watermark、suggestion 或整份 `smartSortResult`。照片、三个 ByPhoto 映射和 `smartSortResult` 继续由现有自动工作台快照持久化；软件重启后 ignored 状态、暂停后的 membership 和可还原前态必须保持。

## 马克开放平台照片结构化导入版

状态：第一、二、三阶段已封版；第四阶段前三刀已封版，第四刀第一小步照片查询与可信会话开发中。

## 1. 总体架构

```text
马克 API 查询
→ 用户勾选照片
→ 主进程事务式下载
→ 保存来源清单与结构化数据
→ 生成工作台导入包
→ 追加并去重进入现有工作台
→ 人工确认
→ 复用现有预览、归档和台账流程
```

核心原则：新增照片来源，不新建平行归档系统。

马克照片默认使用平台结构化字段。本地照片继续使用 OCR；马克照片仅在用户主动选择时使用 OCR 或 AI 作为异常补充。

## 2. 安全与存储边界

- 组织 KEY 只在 Electron 主进程使用。
- 使用 Electron `safeStorage` 加密后保存到 `userData`。
- 前端只能读取是否已配置、组织 ID、更新时间和连接状态。
- KEY 不得进入设置导出、备份、日志、错误详情、前端草稿或 IPC 返回值。
- 签名计算和 API 请求统一在主进程执行。
- 便携版移动到其他 Windows 用户或设备后，应要求重新输入 KEY。

正式下载目录：

```text
文档\物业工作照片归档助手\marki-import\
  <orgId>\
    <teamId>\
      <拍摄日期>\
        <momentId>.jpg
```

来源清单与正式照片使用同一套文档数据根目录：

```text
文档\物业工作照片归档助手\marki-import\
  <orgId>\
    source-manifest.json
```

- 生产调用由 Electron 主进程传入 `app.getPath('documents')`，或传入由现有 `settingsService` 确定的文档数据根目录。
- 来源清单服务保留 `documentsPath` 参数，便于自检传入系统临时目录。
- `.runtime` 只用于开发测试，不得作为正式来源清单或业务照片目录。
- `userData` 只保存安全凭证等内部配置，不得将正式照片和来源清单迁移到 `userData`。

V3.2 第一阶段“马克平台 API 基础能力”已经人工验证通过并封版：

```text
团队不自动选中
```

第二阶段范围冻结为：


### 第二阶段第一刀

第一刀只建立来源清单与去重底座：

```text
sourceKey = marki_api:<orgId>:<momentId>
来源记录持久化
importStatus = discovered
按 sourceKey 查询是否存在
批量去重判断
```

来源清单按组织保存：

```text
marki-import\<orgId>\source-manifest.json
```

写入要求：

- 相同 `sourceKey` 幂等更新，不重复创建记录。
- 使用进程内写入队列避免并发覆盖。
- 先写临时文件并同步到磁盘，再原子替换正式清单。
- 清单损坏时停止写入，不得静默覆盖为空清单。
- 第一刀只保存来源身份摘要，不保存完整远程 URL、原始 content 或组织 KEY。
- 第一刀允许的 `importStatus` 只有 `discovered`。
- 第一刀读取清单时遇到 `downloading`、`imported`、`download_failed` 或其他未知状态，必须按损坏清单保护逻辑拒绝读取，不得静默改写为 `discovered`。
- `downloading`、`imported`、`download_failed` 在第二刀实现事务下载时再正式加入状态集合。

第一刀不下载照片，不新增页面，不接工作台，不做字段映射，不修改归档和台账服务。

### 第二阶段第二刀

第二刀在来源清单底座上加入事务式 JPG 下载：

```text
discovered / download_failed / 中断的 downloading
→ downloading
→ 下载到 <momentId>.jpg.part
→ 校验 HTTP 状态
→ 校验文件非空和大小上限
→ 校验 JPEG 文件头
→ 解析并校验图片宽高
→ 原子改名为 <momentId>.jpg
→ imported
```

状态规则：

- `discovered` 只能进入 `downloading`。
- `download_failed` 可以重新进入 `downloading`。
- 中断遗留的 `downloading` 可以重新开始下载，并累计尝试次数。
- `downloading` 在下载、写盘、校验或原子改名失败后进入 `download_failed`；正式 JPG 完成后的清单提交失败保持 `downloading`，等待重试补记。
- `imported` 不允许重新进入下载状态；同一 `sourceKey` 再次请求时直接返回已导入结果。
- 未知状态继续按损坏清单保护逻辑拒绝，不得静默改写。

文件与安全规则：

- 正式路径保持为 `文档\物业工作照片归档助手\marki-import\<orgId>\<teamId>\<拍摄日期>\<momentId>.jpg`。
- `.part` 与正式 JPG 位于同一目录，只有通过全部校验后才执行原子改名。
- 下载失败时清理 `.part`，保留来源记录、受控错误码、短错误信息和尝试次数，允许用户重试。
- 来源清单只保存相对文件路径、文件名、大小、宽高、SHA-256 和完成时间。
- 完整远程 URL 只在单次下载期间存在于主进程内存，不写入来源清单、日志或错误信息。
- 下载请求使用手工重定向，每一跳都在发出下一次请求前解析并校验协议，只允许 HTTPS。
- 最多允许五次重定向；超过次数、缺少 `Location`、地址无法解析或协议不是 HTTPS 时返回受控错误，错误摘要不得包含重定向地址。
- HTTPS 跨主机重定向允许继续，但每一跳都必须重新校验。
- 不覆盖目标位置中无法通过校验的既有文件。

正式 JPG 与来源清单属于两个独立文件，无法形成跨文件原子事务。恢复规则冻结为：

- 正式 JPG 原子改名完成后，再提交来源清单的 `imported` 状态。
- 如果正式 JPG 已完成但 `imported` 清单提交失败，保留正式 JPG 和原 `downloading` 状态，不得误记为普通 `download_failed`。
- 对外只返回 `marki_manifest_commit_failed` 和固定安全消息，不暴露原始文件系统异常、完整路径或远程 URL。
- 下次重试优先检查正式 JPG；校验通过时不再请求网络，直接补记 `imported`。
- 补记仍失败时继续保留正式 JPG，并再次返回受控清单提交错误。
- 正式 JPG 存在但校验失败时继续执行 `target_file_conflict` 保护，不覆盖、不删除。

第二刀仍不接页面和工作台，不做字段映射，不修改归档、Excel 台账或本地 OCR 流程，不处理视频，也不自动删除来源照片。

### 第三阶段：结构化数据转换

第三阶段只建立主进程后端的数据转换能力：

```text
马克 content
→ 解析字段对
→ 规范字段名
→ 清洗占位值
→ 日期、项目、分类和工作内容映射
→ 生成 recognitionResultsByPhoto
→ 生成 watermarkRecordsByPhoto
→ 生成 archiveSuggestionsByPhoto
→ 组装工作台导入包
```

本阶段输入为马克照片 API 记录、第二阶段已完成的 `imported` 下载结果和当前项目/分类配置。只有 `momentType = 1` 且已完成事务式下载的 JPG 可以生成导入包。

字段清洗规则：

- 支持马克 `content` 的 JSON 字符串、字段对数组和普通字段对象。
- `拍摄日期`、`拍照日期` 统一为 `日期`；`拍摄时间`、`拍照时间` 统一为 `时间`。
- `项目`、`项目名称`、`小区` 统一为 `小区名称`。
- `地址`、`位置`、`客户位置`、`发现地点` 统一为 `地点`。
- `请输入...`、`请选择...`、`请填写...`、`未填写`、`未设置`、`暂无`、`null`、`undefined`、横线、空字符串和纯空格在映射前过滤。
- `null` 和 `undefined` 按完整值不区分大小写过滤；数字 `0`、字符串 `0` 和正常包含“无”的业务文本不得误删。
- 字段容器使用无原型对象，`__proto__`、`prototype`、`constructor` 在键名基本清洗后显式拒绝。
- 同一字段出现多个不同有效值时保留首个值，并生成待核对提示。
- `content` 解析失败不得阻止照片进入工作台导入包，但识别结果标记为结构化数据异常，并要求手工补充或由用户主动选择 OCR。

日期与位置规则：

```text
日期字段中的日期
→ 时间字段中的日期
→ postTime 的东八区日期
```

- 日期或时间字段中包含实际拍摄时间时，生成东八区 `capturedAt`。
- 水印只有时分秒而没有日期时，以 `postTime` 的东八区日期补足日期，但保留水印实际时间。
- 使用 `postTime` 兜底时必须生成提示，且不得把它伪装成水印实际日期。
- `地点` 优先于经纬度；没有地点时，有效经纬度可以形成辅助位置。
- 经度和纬度必须同时为有限数字、位于合法范围且均不等于 `0`，才可形成辅助位置。
- `(0, 0)`、`(0, lat)`、`(lng, 0)`、越界值和非有限数字均属于合法空位置，不报错，也不在映射层写入“现场”。

项目和分类匹配规则：

- 项目只按现有项目名称、项目配置中的别名或调用方提供的明确别名表匹配。
- 分类只按现有分类名称、分类配置中的别名或明确的水印名称映射表匹配。
- `时间地点（兜底选择）` 明确映射到现有的 `时间地点水印` 分类。
- 未匹配项目或分类时只保留候选值，必须由用户确认，不自动创建配置，也不静默写入现有表单值。
- 不把“其他”作为未知项目或未知分类的自动兜底。
- 归档建议必填项固定为日期、项目、归档分类、工作内容四项；任一项缺失或未匹配时状态为 `needs_completion`。

工作内容规则：

- 普通水印按 `工作内容 → 标题` 生成工作内容。
- 机动车水印按 `违停类型｜车牌号` 组合工作内容。
- 标题、施工单位、违停类型和车牌号可形成辅助关键词。
- 防伪码只属于来源追踪信息，不进入工作台导入包的关键词、备注或识别原文。

来源元数据引用固定为：

```text
marki_source_metadata:<orgId>:<momentId>
```

来源元数据正式路径固定为：

```text
文档\物业工作照片归档助手\marki-import\
  <orgId>\
    source-metadata\
      <momentId>.json
```

来源元数据只允许保存：

```text
schemaVersion
sourceMetadataRef
sourceKey
sourceType
orgId
momentId
teamId
uid
postTime
capturedAt
markName
antiCounterfeitCode
parsedEntries
createdAt
updatedAt
```

- `antiCounterfeitCode` 保存清洗后的防伪码，来源元数据服务必须自行再次过滤空值、横线、未填写、未设置、暂无、`null` 和 `undefined` 等占位内容。
- `parsedEntries` 使用 `{ key, value }` 数组保存清洗后的合法原始条目，保留输入顺序及重复字段关系；特殊键、占位值、对象值和不可序列化值不得进入该数组。
- 转换过程可以使用无原型 `fields` 映射并按首个有效值生成业务建议，但 `fields` 和临时 `parsedFields` 不属于来源元数据正式白名单。
- 不保存组织 KEY、签名、请求头、完整远程 URL、原始 `content` 或完整 API 响应。
- 同一引用更新同一个 JSON 文件；写入采用同目录临时文件、磁盘同步和原子替换。
- 已有元数据损坏时拒绝覆盖，错误只返回受控代码和安全短消息。
- 生产调用由主进程传入 Documents 数据根目录；第三阶段只提供持久化服务，不接主进程 IPC。

工作台导入包结构保持为：

```javascript
{
  batchId,
  photos,
  recognitionResultsByPhoto,
  watermarkRecordsByPhoto,
  archiveSuggestionsByPhoto
}
```

照片对象增加并保留：

```text
sourceType = marki_api
sourceKey = marki_api:<orgId>:<momentId>
sourceMetadataRef = marki_source_metadata:<orgId>:<momentId>
capturedAt
```

- `sourceMetadataRef` 与 `sourceKey` 相互独立，指向对应的后端来源元数据记录，不向前端暴露真实存储路径。
- 照片对象使用第二阶段下载后的 `originalPath`、`originalName` 和本地 `previewUrl`。
- 同一导入包内按 `sourceKey` 去重，保留首项并在外层 bundle 返回稳定的重复项统计。
- 正式识别模型支持 `source = marki_api`、`providerType = structured_data`。
- 有效结构化数据使用现有工作台认可的成功状态 `status = recognized`；该状态不依赖 OCR 原始文本，`content` 解析失败仍使用受控失败状态。
- 无论字段是否完整，归档建议都保持 `needsHumanReview = true`，不得自动确认、自动归档或跳过现有人工确认链路。
- 远程 URL、原始 `content`、完整 API 响应、防伪码、组织 KEY 和签名信息不得进入工作台导入包。

转换服务同时提供纯 bundle：

```javascript
{
  workbenchImportPackage,
  sourceMetadataRecordsByRef,
  deduplication
}
```

- `workbenchImportPackage` 仍严格保持原五字段结构，不增加第六个顶层字段。
- `sourceMetadataRecordsByRef` 以 `sourceMetadataRef` 为键，每张工作台照片必须有且只有一条对应来源记录。
- `deduplication` 固定包含 `inputCount`、`uniqueCount`、`duplicateCount` 和 `skippedItems`；每个跳过项只保存 `sourceKey`、`keptInputIndex` 和 `skippedInputIndex`。
- 当前仅完成同一 bundle 内的批内去重，尚未连接正式工作台，不声称已经完成工作台已有照片的全局去重。
- 纯 bundle 只生成可 JSON 序列化的数据，不写盘、不请求网络，也不修改输入对象。
- 后续接主进程时必须按“生成 bundle → 保存全部来源元数据 → 确认全部成功 → 交付五字段工作台包”的顺序编排。
- 多条来源元数据分别写入独立 JSON 文件，不声称多个文件之间具备跨文件原子事务；中途失败时已成功文件可以幂等复用，但整批工作台包不得提前交付。

第三阶段仍不接 Electron 主进程 IPC、前端查询页面和现有工作台状态；不执行正式归档，不修改 Excel 台账，不处理视频，不自动创建项目或分类，也不修改本地 OCR 流程。

### 第四阶段第一刀：主进程编排底座

第四阶段第一刀只建立后端编排服务，不注册 IPC，不建立页面，也不把照片实际追加到工作台。公开入口固定为：

```javascript
prepareMarkiStructuredImport({
  documentsPath,
  orgId,
  items
}, options)
```

- `documentsPath` 必须由未来 Electron 主进程明确传入正式 Documents 数据根目录，服务不得回退到 `userData` 或其他默认目录。
- `orgId` 为当前马克组织 ID，`items` 为第二阶段已经完成事务式下载且状态为 `imported` 的照片记录。
- 项目和分类配置只通过 `loadConfigs(documentsPath)` 读取，不接受前端输入配置，不使用默认项目、默认分类或硬编码兜底。
- 编排服务复用 `buildMarkiStructuredImportBundle()` 生成第三阶段 bundle，并复用 `saveMarkiSourceMetadata()` 保存来源元数据，不复制字段映射、清洗、去重或持久化逻辑。

固定返回结构为：

```javascript
{
  success,
  batchId,
  inputCount,
  metadataSavedCount,
  failedCount,
  failures,
  deduplication,
  workbenchImportPackage
}
```

其中 `success = failedCount === 0`，`inputCount` 为原始输入数量。只有所有来源元数据都保存成功时，`workbenchImportPackage` 才返回第三阶段定义的五字段工作台包；任何一条来源元数据保存失败时，该字段必须为 `null`。

来源元数据按 `sourceMetadataRef` 的确定顺序逐条保存。每条记录继续使用来源元数据服务的单文件临时写入和原子替换能力；多个独立元数据文件之间不构成跨文件原子事务。单条失败时：

- 记录安全失败摘要并继续尝试后续记录。
- 已经成功保存的独立元数据文件不回滚、不删除。
- 整批工作台包暂不交付。
- 用户重试整批时复用同一 `sourceMetadataRef` 的幂等保存能力，补齐失败记录，不生成重复文件。

`failures` 每项只允许包含：

```javascript
{
  sourceMetadataRef,
  sourceKey,
  code,
  message
}
```

失败摘要不得包含 Documents 路径、本地照片路径、远程 URL、原始 `content`、`parsedEntries`、防伪码、原始异常对象、堆栈、组织 KEY 或签名信息。整批输入无效、配置读取失败或 bundle 构建失败时返回固定代码和安全短消息，不透传底层异常。

本刀不包含 Electron 主进程 IPC、preload、批次存储目录、查询或导入页面、现有工作台合并与全局去重，也不修改归档、Excel、本地 OCR、照片下载和来源清单服务。第二刀及其页面衔接能力尚未实现。

### 第四阶段第二刀：导入批次临时持久化与受控 IPC

第二刀只建立内部临时批次协调能力。批次文件固定保存在：

```text
app.getPath('userData')\marki-import-batches\<batchId>.json
```

- 批次不属于正式来源资料，不写入 Documents 下的 `marki-import`，也不写入项目源码、照片下载目录或 renderer 指定的位置。
- `userDataPath` 只由 Electron 主进程通过 `app.getPath('userData')` 提供，renderer 不得传入目录、文件名或任意文件路径。
- 每个批次文件使用同目录唯一临时文件、独占创建、写入后 `sync`、关闭文件及安全替换；失败时清理本次临时文件。
- 同一 `batchId` 的写入、查询清理和消费使用进程内串行锁。不同批次之间不构成跨文件事务。
- 已有批次 JSON 损坏时拒绝读取和覆盖，保留原文件供人工恢复。

批次状态固定为：

```text
不存在 → preparing
preparing → ready
preparing → failed
failed → preparing
ready → consumed
```

禁止 `ready` 回退到 `preparing` 或 `failed`，也禁止 `consumed` 回退到任何可交付状态。`failed → preparing` 只用于整批幂等重试，并要求输入数量和批内去重统计与原失败批次一致。

批次记录 `schemaVersion = 1`，固定保存：

```text
schemaVersion
batchId
status
inputCount
metadataSavedCount
failedCount
failures
deduplication
workbenchImportPackage
createdAt
updatedAt
expiresAt
consumedAt
```

- `batchId` 只允许字母、数字、下划线和横线，拒绝点号、路径分隔符、控制字符和路径穿越。
- `preparing` 与 `failed` 的 `workbenchImportPackage` 必须为 `null`。
- `ready` 必须保存第三阶段定义的严格五字段工作台包，包内 `batchId` 必须与批次一致，不允许第六个顶层字段。
- 工作台包深拷贝后保存和返回，批次服务不修改照片、识别结果、水印记录或归档建议的业务内容。
- `consumed` 立即清除工作台包，只保留短期防重复消费的墓碑记录。
- `failures` 继续严格使用 `sourceMetadataRef`、`sourceKey`、`code`、`message` 四字段安全白名单。
- 批次不得保存原始异常、堆栈、组织 KEY、签名、完整远程 URL、原始 `content`、`parsedEntries`、防伪码或 API 原始响应。

生命周期固定为：

```text
preparing  1 小时
ready      24 小时
failed     24 小时
consumed   10 分钟墓碑
```

过期批次清理后不得继续返回旧工作台包。时间计算由服务统一完成，自动自检可以通过 `options.now` 注入确定时间。

查询入口 `getMarkiImportBatch(userDataPath, batchId)` 不改变状态。`ready` 返回五字段工作台包；`preparing`、`failed` 和 `consumed` 只返回安全状态摘要，工作台包固定为 `null`。查询结果不包含内部批次文件路径。

消费入口 `consumeMarkiImportBatch(userDataPath, batchId)` 只允许 `ready → consumed`：

- 首次消费返回 `alreadyConsumed = false`，不返回工作台包。
- 对尚未过期的 `consumed` 墓碑重复消费时，幂等返回 `alreadyConsumed = true`。
- `preparing` 和 `failed` 不得消费。
- 并发消费通过同一批次串行锁保证只有一次真实状态转换。

Electron 主进程只注册：

```text
marki:get-import-batch
marki:consume-import-batch
```

马克联网 API 继续使用 `safeMarkiCall`，由该包装加载组织凭证后执行请求。本地批次查询和消费使用独立的 `safeMarkiLocalCall`：直接执行本地服务，不读取组织 KEY，不调用 `loadMarkiCredentials`，也不依赖 `safeStorage`。两类调用都通过 `toSafeMarkiError` 输出安全错误，不返回原始异常、堆栈或内部批次路径。

两个本地批次 IPC 仍由主进程固定传入 `app.getPath('userData')`，renderer 只能传 `batchId`。preload 接口保持 `getImportBatch(batchId)` 和 `consumeImportBatch(batchId)`，不增加路径参数或其他写入能力。

本刀不注册 `marki:prepare-structured-import`。在主进程尚未建立照片查询缓存或安全选择令牌前，不允许 renderer 传入完整 moment、远程 URL、原始 `content` 或下载结果。第二刀不建立照片查询页面，不把批次追加到现有工作台，不实现工作台 `sourceKey` 全局合并去重，不修改归档、Excel、本地 OCR 或 React 状态。

### 第四阶段第三刀：批次进入现有工作台与全局去重

第三刀复用现有照片分拣工作台，不创建第二套工作台。导航请求固定为：

```javascript
{
  page: PAGE_KEYS.sortWorkspace,
  action: 'appendMarkiImportBatch',
  payload: {
    batchId
  },
  nonce
}
```

`MainRouter` 在历史快速归档入口和正式分拣工作台入口均向 `SortWorkspacePage` 传递 `navigationRequest`。工作台只在会话状态完成恢复、action 精确匹配、`batchId` 非空且 nonce 尚未处理时查询批次；同一 nonce 在查询前登记，防止 StrictMode 或重复渲染导致重复查询和消费。

工作台先通过 `getImportBatch(batchId)` 读取批次。`preparing`、`failed`、`consumed` 和安全错误只更新现有状态提示，不修改照片或工作台映射。只有 `ready` 且存在严格五字段工作台包时，才调用纯函数：

```javascript
mergeMarkiWorkbenchImportPackage(currentState, workbenchImportPackage)
```

纯函数输入中的工作台包严格只有：

```text
batchId
photos
recognitionResultsByPhoto
watermarkRecordsByPhoto
archiveSuggestionsByPhoto
```

每张输入照片必须具有非空 `id`、`sourceType = marki_api` 和以 `marki_api:` 开头的 `sourceKey`，并在三个 `ByPhoto` 映射中都有对应记录；映射不得包含孤立照片 ID，不接受第六个顶层字段或 `__proto__`、`prototype`、`constructor` 等特殊键。校验失败时整体拒绝，不返回部分结果，也不触发任何工作台状态更新或批次消费。

全局合并规则固定为：

- 当前工作台已有照片与本批前面已接受照片共同建立 `sourceKey` 和照片 ID 占用集合。
- incoming `sourceKey` 已存在时按 `duplicate_source_key` 跳过，无论照片 ID 是否相同。
- incoming 照片 ID 已被旧照片、旧映射或本批已接受照片占用，而 `sourceKey` 不同时按 `conflicting_photo_id` 跳过。
- 没有 `sourceKey` 的旧本地 OCR 照片保持原对象和原行为，只通过照片 ID 防止冲突。
- 不同组织的相同 moment ID 以完整 `marki_api:<orgId>:<momentId>` 判断，不互相误判重复。

五类工作台数据按以下方式同步追加：

- `photos` 只在旧数组末尾追加被接受的新照片，不重建或修改旧照片对象。
- 三个 `ByPhoto` 映射只追加被接受照片对应的键；重复项和冲突项同步跳过，旧键绝不覆盖。
- `selectedIds` 保留原顺序和原选择，并追加所有新增照片 ID，不产生重复。
- 有新增照片时 `activePhotoId` 切换到第一张新增照片；没有新增照片时保持原值。
- 合并统计固定返回输入数、新增数、重复数、冲突数和安全跳过摘要。

有新增照片时，工作台退出状态筛选、搜索和智能分组视图限制，但不清除已有智能分组结果，也不修改排序模式。第一张新增照片通过 pending focus 引用在最新 `visiblePhotos` 中查找，再按当前排序和 `pageSize` 计算目标页；目标页和当前照片同步后滚动中间照片区到对应条目。该过程不自动改变原勾选、人工确认结果、预览、归档结果、目录或草稿。

严格顺序为：

```text
getImportBatch
→ 校验并纯计算合并后的完整工作台
→ 原子保存统一工作台自动快照
→ consumeImportBatch
→ 将同一份合并结果提交 React 与 renderer 内存缓存
```

重复和 ID 冲突属于已按规则处理的跳过项，不阻止批次消费。全批均为重复时工作台保持不变，但仍消费批次并提示未重复追加；只有冲突时也不覆盖旧数据，消费后报告冲突数量。纯合并或自动快照失败均不消费批次，也不提交 React 半完成状态。消费失败时自动快照已经包含合并结果，页面提交同一份状态并提示用户再次处理时依靠 `sourceKey` 全局去重避免重复追加。

第三刀仍不新增马克照片查询和选择页面，不注册新 IPC，不修改 preload、导航菜单、页面常量、归档、Excel、本地 OCR、项目分类匹配或样式，也不调用真实马克 API。后续查询页面刀次尚未实现。

### 第四阶段第四刀第一小步：照片查询与主进程可信会话

照片查询使用现有签名请求能力，在主进程内部调用：

```text
POST https://open-api.markiapp.com/marki/moment
```

业务请求仅允许 `teamId`、`uid`、`start`、`end` 和内部分页使用的 `next`。服务固定写入 `momType = 1`，不接受调用方覆盖。`start` 与 `end` 必须是东八区上传时间，格式严格为 `yyyy-MM-dd HH:mm:ss`；开始时间不得晚于结束时间，单次范围最多 31 天。`teamId` 和 `uid` 有值时必须为正整数，按人员查询时必须同时提供团队。分页游标只保存在主进程会话中，不允许 renderer 提交或读取。

查询结果中的完整 moment 只在 Electron 主进程内存中短期保存，包括照片 ID、团队和人员 ID、远程 HTTPS 地址、原始 `content`、水印名、坐标及秒级 `postTime`。查询会话使用模块内存 `Map`，不写入 `userData`、Documents 或源码目录。应用重启后会话自然失效；同一主进程内页面刷新可凭不透明 `sessionId` 恢复。

会话和照片令牌均使用随机 UUID：

- `sessionId` 不编码组织、团队、查询时间或分页信息。
- `selectionToken` 不编码组织 ID、moment ID、远程 URL 或本地路径。
- 同一 sourceKey 在同一会话跨页重复出现时复用首次生成的令牌，不重复生成摘要。
- 完整 moment、sourceKey、真实 moment ID、远程 URL、原始 `content` 和真实 `next` 不经 IPC 返回 renderer。

会话限制固定为：

```text
空闲期限       15 分钟
硬期限         30 分钟
最大有效会话   3 个
单会话照片上限 1000 张唯一照片
```

创建新会话前先清理过期会话；达到三个有效会话时安全拒绝，不删除仍有效会话。达到 1000 张后停止追加和后续网络分页，返回 `limitReached = true`，并向 renderer 统一显示 `hasMore = false`。

renderer 每张照片只接收以下安全摘要：

```text
selectionToken
displayId
teamId
uid
photographerName
markName
watermarkKey
isWatermarked
postTime
displayDate
projectText
workContentText
locationText
selectedSourceStatus
```

`displayId` 是会话内顺序号，不是真实 moment ID；`displayDate` 将秒级 `postTime` 按 UTC+8 格式化。项目、工作内容和地点复用现有结构化 `content` 解析能力，只输出清洗后的安全文本。当前没有可信成员昵称缓存时 `photographerName` 为空。`watermarkKey` 是可信水印名称的规范化筛选身份，`isWatermarked` 是主进程判定结果。`selectedSourceStatus` 由主进程只读组合正式来源清单、导入 lifecycle ledger 和当前工作台快照，映射为本节后续定义的完整安全生命周期；查询不创建或修改来源记录、工作台或下载缓存。

首次查询、下一页和会话恢复统一返回当前会话已经加载的全部安全摘要，以及：

```javascript
{
  loadedCount,
  pageCount,
  hasMore,
  limitReached
}
```

返回结果不包含真实分页游标。下一页请求只接收 `sessionId`，主进程使用会话内原始筛选和 cursor 继续查询，并校验当前安全凭证中的组织 ID 与会话一致；组织变化时旧会话立即失效。

本步注册四个受控 IPC：

```text
marki:start-photo-query-session
marki:get-photo-query-session
marki:load-next-photo-query-page
marki:destroy-photo-query-session
```

`start` 和 `load-next` 需要网络及组织凭证，使用 `safeMarkiCall`。首次查询由主进程固定注入 `app.getPath('documents')`；renderer 只能提交团队、人员、开始时间和结束时间。`get` 和 `destroy` 只处理内存会话，使用 `safeMarkiLocalCall`，不读取组织 KEY，不依赖 `safeStorage`。四个入口都通过现有安全错误结构收口，不返回原始异常、堆栈、路径、凭证或 API 原始响应。

本步只建立照片查询 API、主进程可信会话、不透明选择令牌、安全摘要和查询会话 IPC；不下载照片，不写来源记录或来源元数据，不创建批次，不调用结构化导入编排，不修改工作台，也不执行归档和 Excel 写入。

### 第四阶段第四刀第二小步：可信选择导入与批次生成

renderer 发起导入时只能提交：

```javascript
{
  sessionId,
  selectionTokens,
  watermarkFilter,
  importStatusFilter
}
```

主进程拒绝任何额外字段，并通过查询会话恢复可信 moment、sourceKey、远程 URL 和原始结构化内容；两个筛选值只用于对可信会话结果和实时 lifecycle 状态进行一致性复核，不能改变 moment 或 sourceKey。会话内部为每个选择令牌维护 `idle`、`in_progress`、`failed`、`completed` 四种导入任务状态；同一令牌不得并发导入，失败任务只能使用原 token 集合重试。不同会话同时导入相同 sourceKey 时通过进程内原子占用整批拒绝，所有成功和失败路径均释放占用。

普通导入重新组合正式 Documents 来源清单、userData lifecycle ledger 和工作台快照。只有工作池当前存在或未完成事务仍占用的 sourceKey 才阻止重复导入，历史 manifest `imported` 不再永久阻止。失败任务重试时保留原有效照片集合，即使部分照片已在前次尝试中完成下载，也继续纳入同一任务并复用正式 JPG。`downloadMarkiPhoto` 对 `imported` 记录不再只信任清单，而是重新核验缓存路径边界、文件存在、普通文件、JPG 文件头、字节数、宽高和 SHA-256；普通复验失败不覆盖文件、不自动联网。只有用户主动重导或失败重试时才允许把失效缓存转入受控重下，损坏旧文件先隔离，新下载成功后再清理隔离文件。新下载和复用结果均返回 `completedAt`。

开始下载前先生成 batchId 并持久化 lifecycle ledger，随后最多三路并发下载，结果顺序与 selectionToken 顺序一致。任一下载失败时不创建可进入工作台的临时 ready 批次，不局部交付工作台；已经成功的 JPG 和 lifecycle 单项状态保留，批次进入 `failed` 或 `partial_failed`。renderer 可见的每条失败摘要严格为 `selectionToken`、`displayId`、`code`、`message` 四字段，其中 `displayId` 来自主进程可信查询会话的安全展示编号；缺少合法展示值时只使用稳定的顺序型后备编号，不暴露 momentId、sourceKey、URL、content、组织 ID 或本地路径。重试时已完成 JPG 通过完整性复验零网络复用。

全部下载成功后才执行：

```text
生成或复用 batchId
→ beginMarkiImportBatch
→ prepareMarkiStructuredImport（固定同一 batchId）
→ markMarkiImportBatchReady / markMarkiImportBatchFailed
```

来源元数据局部失败时批次为 `failed`，成功元数据文件保留，工作台包固定为 `null`；重试通过 `failed → preparing` 复用同一 batchId 幂等补齐。批次写入失败返回 `batch_persist_failed`，不把工作台包返回 renderer。全部成功只返回安全统计和 batchId。

ready 批次发现入口 `listReadyMarkiImportBatches` 只返回：

```text
batchId
status
inputCount
metadataSavedCount
createdAt
updatedAt
expiresAt
```

不返回工作台包、照片、来源键、失败明细或内部路径。列表顶层固定返回 `{ success, items, failedCount }`，其中 `items` 为上述七字段安全批次数组。批次目录中的单个损坏 JSON、读取失败或结构非法文件只计入 `failedCount`，不阻断其他正常 ready 批次；列表操作只读，不修改批次状态、不删除过期或损坏文件。本步新增 `marki:import-photo-query-selection`（需要凭证）和 `marki:list-ready-import-batches`（本地安全调用）两个 IPC。正式来源目录固定使用 `app.getPath('documents')`，临时批次目录固定使用 `app.getPath('userData')`。

### 统一工作台第一刀：自动快照、启动恢复与安全消费顺序

照片分拣工作台新增单一自动快照，由 Electron 主进程持久化到：

```text
app.getPath('userData')/sort-workspace/active-workbench.json
```

renderer 只能提交经过白名单构造的工作台对象，不能传入 `userDataPath`、目录或文件名。自动快照与 Documents 中用户手工选择保存的分拣草稿互相独立，不弹出文件选择框，也不覆盖手工草稿。

快照 schema 固定为：

```javascript
{
  schemaVersion: 1,
  savedAt,
  workspace: {
    photos,
    selectedIds,
    activePhotoId,
    recognitionResultsByPhoto,
    watermarkRecordsByPhoto,
    archiveSuggestionsByPhoto,
    smartSortResult,
    smartSortViewMode,
    activeSmartSortGroupId,
    photoFolder,
    archiveRoot,
    filter,
    sortMode,
    pageSize,
    rightPanelMode,
    form,
    searchText,
    page,
    viewMode
  }
}
```

照片对象继续保存人工归档信息、已确认状态、归档预览、归档结果以及 `sourceType`、`sourceKey`、`sourceMetadataRef`。`searchText`、页码和视图模式用于恢复用户离开前的工作上下文。busy、progress、临时错误、React ref、DOM、Promise、AbortController、原始 Set/Map 不进入快照。

保存服务使用字段白名单和递归结构净化，限制最多 10000 张照片、32MB 快照和有限嵌套深度。运行期 `previewUrl`、`thumbnailPath` 可以作为输入存在，但保存时剥离；恢复时根据受信任的本地 `originalPath` 重新生成当前运行期预览地址。远程 URL、原始 `content`、完整 moment、API 响应、KEY、签名、请求头和异常堆栈均不保存。

每次保存采用同路径进程内串行队列和原子替换：

```text
验证并净化
→ 同目录唯一临时文件独占创建
→ 写入
→ sync
→ close
→ rename 替换正式快照
→ 清理临时文件
```

现有正式快照损坏时拒绝覆盖，避免静默清空可恢复资料。JSON 损坏、结构非法或 schemaVersion 不兼容时返回固定安全错误，不返回损坏内容或内部快照路径，也不阻止用户进入安全空工作台。加载时逐张检查 `originalPath`；单张原图缺失只标记该记录为 `originalMissing` 并保留原分拣状态，其他照片继续恢复。

普通状态变化使用 500ms 防抖、单通道串行和最后状态优先策略。保存失败后队列会释放，后续状态仍可继续尝试。初始化完成前自动保存保持关闭，启动顺序为：

```text
加载配置和目录
→ 加载并验证自动快照
→ 恢复统一照片池、三个 ByPhoto 映射、选择、当前照片、智拣、表单和视图
→ 启用自动保存
→ 标记工作台已 hydrated
→ 处理 appendMarkiImportBatch 导航请求
```

同一 renderer 中已有会话缓存时保留当前页面状态；软件重启没有 renderer 缓存时从主进程快照恢复。快照不存在则维持原空工作台行为。扫描覆盖、清空工作台、手工草稿恢复、归档完成和 Marki 批次追加均执行显式立即快照；手工草稿仍使用原按钮和文件格式，旧草稿缺少自动快照字段时使用安全默认值。

Marki ready 批次的数据安全顺序固定为：

```text
读取严格五字段工作台包
→ mergeMarkiWorkbenchImportPackage 计算一次合并结果
→ 立即原子保存合并后的完整工作台
→ 快照成功后 consumeImportBatch
→ 将同一合并结果提交 React 和 renderer 会话缓存
```

快照失败时不调用 consume，批次保持 ready，React 工作台不留下只存在内存的半完成追加。consume 失败时快照已经包含照片，页面保留同一合并状态；用户重试同一 batchId 时通过全局 `sourceKey` 去重，不会重复追加，随后可完成消费。

自动验证使用系统临时目录和本地测试照片，真实覆盖 17 个行为场景、58 个行为断言和 7 个源码契约断言，包括：无快照、完整保存、删除 require cache 后全新服务实例恢复、三类映射和智拣恢复、Marki 来源字段恢复、单张原图缺失部分恢复、原子 rename 失败保留旧快照、损坏与不兼容保护、防抖最终状态、串行写入、失败后重试、初始化禁写、先快照后消费、快照失败零消费、consume 失败后幂等重试，以及恢复后继续追加新 Marki 批次。测试不使用查询会话、凭证或网络。

### 统一工作台第二刀：历史 imported Marki 照片本地恢复

针对统一工作台自动快照上线前已经完成下载、来源清单状态为 `imported`，但旧批次已经 `consumed` 且工作台包已清除的历史照片，提供“恢复已下载的马克照片”入口。恢复完全基于本机正式来源资料：

```text
Documents/物业工作照片归档助手/marki-import/<orgId>/source-manifest.json
Documents/物业工作照片归档助手/marki-import/<orgId>/source-metadata/<momentId>.json
Documents/物业工作照片归档助手/marki-import/<orgId>/<teamId>/<日期>/<momentId>.jpg
userData/sort-workspace/active-workbench.json
```

恢复不读取组织凭证，不建立查询会话，不请求真实马克 API，不重新下载照片，不创建或消费批次，也不修改来源清单、来源元数据、JPG 和历史批次。`imported` 只证明事务下载已经完成，不等于照片当前仍在工作台或已经完成正式归档。

主进程扫描所有组织清单时逐条隔离损坏记录，候选状态固定为：

```text
recoverable
already_in_workbench
already_archived
missing_file
corrupted_file
missing_metadata
invalid_record
```

`already_in_workbench` 与 `already_archived` 只以当前受信任自动快照中的同一 `sourceKey` 为依据；当前版本不根据 consumed 批次推断归档状态。renderer 每项只获得：

```javascript
{
  recoveryToken,
  displayId,
  capturedAt,
  photographerName,
  projectName,
  status
}
```

`recoveryToken` 为随机不透明令牌。renderer 不获得 sourceKey、momentId、来源元数据引用、本地路径、远程 URL、原始 content、防伪码、parsedEntries 或工作台包，也只能向主进程提交严格的 `{ recoveryTokens }`。

工作台工具栏只保留短文案“恢复 Marki 照片”。点击后立即关闭“更多”菜单，并通过 React portal 在 `document.body` 打开独立恢复对话框。对话框不挂载在照片网格、中栏滚动区、左右面板或工具栏菜单内；标题、状态摘要和底部操作区固定，候选列表在对话框内部独立滚动。对话框继续只显示安全摘要和状态统计，不显示 sourceKey、本地路径、URL、哈希或内部异常。关闭对话框不得改变当前选择和活动照片。

恢复前必须重新读取来源清单和当前自动快照，并对每张照片执行：

```text
relativePath 目录边界和符号链接逃逸检查
→ 普通文件检查
→ JPEG 文件头检查
→ 宽高校验
→ 文件大小校验
→ SHA-256 与来源清单逐项比对
→ 来源元数据白名单、sourceKey、orgId、momentId 和引用一致性校验
```

来源元数据中的 `parsedEntries` 与防伪码只在主进程内重建现有结构化转换输入，继续复用 `buildMarkiStructuredImportBundle` 生成 recognition、watermark 和 archive suggestion；不发明缺失字段，不自动确认，不自动归档。Electron 与 renderer 共用同一份纯 `mergeMarkiWorkbenchImportPackage` 核心，继续执行 sourceKey 全局去重和 photo.id 冲突保护。

安全事务顺序固定为：

```text
重新验证所选恢复令牌和来源资料
→ 读取当前自动快照
→ 复用现有结构化转换
→ 复用现有工作台合并规则
→ 原子保存合并后的自动快照
→ renderer 重新加载已落盘快照
```

自动快照保存失败时不更新 renderer，不改变任何来源资料；重新扫描和重试即可。保存成功后，即使 renderer 刷新失败，软件重启也会从自动快照恢复照片。重复扫描、重复操作或扫描后的并发状态变化均通过当前快照中的 `sourceKey` 再次去重，不产生重复照片。

自动验证真实建立 consumed 历史批次、本地 JPG、来源清单和来源元数据，并单独验证完全没有旧自动快照时的恢复；共覆盖 27 个行为场景和 73 个断言，其中 9 个为源码契约断言。同时使用恢复服务的真实产物连续执行两次来源感知智拣，确认完整 Marki 两次均不检查 OCR 服务、不调用 OCR，平台三个对象保持不变。测试还包括：成功恢复、重启持久化、本地照片保留、三个 ByPhoto 映射恢复、重复令牌、竞态 sourceKey、缺文件、损坏 JPG、缺元数据、路径逃逸、同清单坏记录隔离、快照不可读和原子保存失败保护。

本刀尚未解决：

```text
imported 与工作台成员状态解耦
清空后重新加入
本地扫描覆盖 Marki 的保护
Marki 归档与 Excel 来源追溯
入口与页面搬迁收敛
```

### 统一工作台第三刀：来源感知智拣

工作台继续保留单一“智拣”入口，根据照片可信来源自动选择处理路径，不增加 OCR 模式或 Marki 模式：

```text
local_file 或旧本地照片
→ 复用原本地 OCR、水印解析和建议生成

marki_api + 四项必要字段完整
→ 直接复用平台 recognition、watermark 和 archive suggestion
→ 不检查 OCR 服务
→ OCR 调用次数为 0

marki_api + 平台基线缺失、但已有 OCR 补充或人工修订已补齐
→ 复用已有补充和当前有效结果
→ 不检查 OCR 服务
→ 不重复 OCR

marki_api + 当前有效结果仍缺少四项必要字段
→ 仅对该照片执行 OCR 兜底
→ 只补充缺失的正式字段
→ 平台已有值优先，冲突只进入人工核查信息
```

四项必要字段的 canonical key 固定为：

```text
date
project
watermarkCategory
workContent
```

位置、详细地址、备注、关键词、拍摄人员和防伪码不是智拣必要字段，缺失时不触发 OCR。完整性以四项正式字段重新计算；未匹配的项目候选文本或原水印名称不能冒充正式项目、分类。外部或旧版本的 `missingRequiredFields` 仅作展示信息，不作为重复智拣的单一判断依据。

Marki 可信结构化基线必须同时满足照片 `sourceType = marki_api`，识别结果 `source = marki_api`、`providerType = structured_data`，以及对应 watermark 和 archive suggestion 的来源与照片标识一致。来源缺失的旧本地照片只有在不带 `sourceKey`、`sourceMetadataRef` 或 Marki 结构化来源标志，且具有现有本地照片标识和原图路径时，才按兼容路径执行本地 OCR；未知或不一致来源不会根据文件名、目录或识别文字猜测为本地或 Marki。

普通“智拣”表示重新评估当前可信结果、按需补缺并重新分组，不表示清空结果后强制重新 OCR。导入和历史恢复只带入平台 recognition、watermark、archive suggestion 并加入工作台，不调用来源感知编排、OCR 或智能分组，也不写入 `sourceAwareProcessing`。完整 Marki 第一次、第二次及后续智拣均稳定走 `marki_platform_only`；已经补齐的 Marki 稳定走 `marki_existing_supplement`；只有当前有效结果仍缺必要字段时才走 `marki_ocr_fallback`。

OCR 兜底成功后，平台 recognition 的结构化字段和 watermark 事实层保持原值。来源感知结果在 recognition 中保存最小、可序列化的三层记录：

```javascript
{
  strategy: 'platform_plus_ocr',
  platformBaseline: {
    source: 'marki_api',
    providerType: 'structured_data',
    requiredFields: {
      date,
      project,
      watermarkCategory,
      workContent
    },
    missingRequiredFields: []
  },
  ocrSupplement: {
    fields: {},
    supplementedFields: [],
    conflicts: []
  },
  effectiveResult: {
    requiredFields: {
      date,
      project,
      watermarkCategory,
      workContent
    },
    unresolvedFields: []
  },
  missingBefore: [],
  supplementedFields: [],
  unresolvedFields: [],
  conflicts: [
    {
      field,
      platformValue,
      ocrValue
    }
  ],
  ocrFallbackStatus: 'completed'
}
```

`platformBaseline` 永久记录首次兜底前的四项平台正式值，`ocrSupplement` 只记录平台缺失字段的有效补充和去重后的字段冲突，`effectiveResult` 用于分组和当前核查。该分层不复制完整 moment，不保存远程 URL、content、完整 API 响应、原始 OCR 结果、异常或堆栈。OCR 失败时不改写平台三个对象，不清空平台数据；当前智拣执行状态标记为 `failed`，并移除该照片已经失效的旧 group membership，缺失字段继续要求人工完善和重试。

混合选择先分别完成本地 OCR、平台直用、已有补充复用和 Marki OCR 兜底，再对全部可用结果执行一次统一 `generateSmartSortGroups`。来源仅用于处理路由和追溯，不强制拆分业务分组。OCR 服务不可用时，完整 Marki 和已有补充 Marki 仍可正常进入分组；本地照片和需要兜底的 Marki 单独报告不可用，不会清除平台基线。

智拣完成后一次性更新照片和三个 ByPhoto 映射，并立即使用现有自动快照保存最终照片状态、识别映射、建议补充层、冲突信息和智能分组；快照失败沿用现有警告与后续重试机制，不扩展为新的事务系统。

### 统一照片池追加与可见智拣结果

本地照片导入、重新扫描和更换来源目录统一采用追加模式，不再以当前目录扫描结果重建整个工作台。主进程扫描服务为每张本地文件流式计算 SHA-256，工作台照片对象和自动快照保存该内容指纹；Marki 工作台照片沿用下载阶段已经校验的 SHA-256。统一照片池按以下顺序处理：

```text
保留全部已有本地和 Marki 照片对象及处理状态
→ 读取扫描结果的可信 SHA-256
→ 对当前整个工作台和本次扫描批次执行内容去重
→ 跳过与已有 Marki、本地照片或本批前项内容相同的照片
→ 只在末尾追加唯一的新本地照片
→ 自动选中新照片并保留原选择和当前照片
```

Marki 导入本身继续按 `sourceKey` 去重；本地照片及本地与 Marki 的跨来源重复最终按 SHA-256 去重。重复照片只跳过，不覆盖已有照片的来源身份、人工修改、确认状态、预览、归档状态或三个 ByPhoto 映射。目录 A 扫描后切换目录 B，目录 A、目录 B 和 Marki 照片共同保留；只有用户明确执行“清空”才清空工作台。

真正追加本地照片后，旧 `smartSortResult` 失效并返回普通照片池视图，但导入阶段不调用 OCR、不执行来源感知智拣、不生成新分组。自动快照在 React 状态提交前保存同一份合并结果，确保重启后仍恢复统一照片池和保留的三个 ByPhoto 映射。

完整 Marki 主动点击“智拣”时，即使 recognition、watermark 和 archive suggestion 三个可信平台对象深比较不变，也属于成功处理。`marki_platform_only` 照片必须计入平台直用统计、参与一次统一生产分组，并通过页面提交适配切换到第一个可见分组，同时保存：

```text
smartSortResult
smartSortViewMode = smartSortGroup
activeSmartSortGroupId
activePhotoId
searchText = 空
page = 1
```

完成提示必须包含“平台数据直用 X 张”。再次点击智拣仍重新计算一次分组，但不检查 OCR 服务、不调用 OCR，也不改写平台三个对象。导入照片不等于完成智拣，只有用户点击“智拣”后才生成和显示分组。

新增自动验证覆盖 6 个行为场景、57 个行为断言和 11 个源码契约断言，真实执行主进程扫描哈希、统一照片池跨目录追加、Marki 与本地跨来源内容去重、来源感知编排、生产智能分组、页面分组提交适配、混合来源一次分组以及自动快照保存和全新实例恢复。测试确认完整 Marki 连续两次 OCR 和 OCR 服务检查均为零，每次各执行一次分组；混合池只对本地照片执行一次 OCR，Marki 平台直用一张，最终只分组一次；扫描 handler 只提交追加结果并使旧分组失效，不自动执行 OCR 或分组。所有文件均位于系统临时目录，不调用真实 Marki API，不使用用户真实照片执行 OCR。

### Marki 智拣显式状态闭环

平台结构化数据是否存在、智拣是否执行以及是否生成分组是三个独立概念。照片使用独立、可持久化的 `smartSortStatus` 表达智拣执行状态：

```text
not_run
running
completed
needs_completion
failed
```

工作台不得再根据 recognition、watermark、archive suggestion 是否存在推断智拣已经执行。完整 Marki 导入或历史恢复后保留三份平台数据，但固定进入 `not_run`，页面显示“待智拣”，不产生 `smartSortResult` 和 group membership。只有来源感知编排完成且正式 `smartSortResult` 中存在该照片的成员记录时，才写入 `completed` 并进入“待整理”；存在未解决必要字段且仍成功参与分组时写入 `needs_completion`，编排或分组失败时写入 `failed`。

“重置智拣结果”只作用于当前选择中允许重置且真实存在智拣结果的照片。先从旧 `smartSortResult` 中移除目标照片 membership，删除空分组并重算统计；未选中照片的状态、membership、人工整理信息和预览保持不变，不得整体清空 `smartSortResult`。Marki 照片的 sourceType、sourceKey、sourceMetadataRef、recognition、watermark、archive suggestion、来源文件和平台基线必须原样保留；本地照片沿用原规则清除本地 OCR 三份派生映射。目标照片回到 `smartSortStatus=not_run`，已归档、正在归档和原图缺失照片不参与普通重置。重置后保持当前选择、活动照片、搜索和筛选，可以再次按来源执行智拣。

完整 Marki 的状态链固定为：

```text
导入
→ 平台数据已加载 + smartSortStatus=not_run + 无分组
→ 用户点击智拣
→ marki_platform_only + OCR=0 + 分组一次
→ smartSortStatus=completed + 可见 group membership
→ 用户重置
→ 平台三对象不变 + smartSortStatus=not_run + 无分组
→ 用户再次点击智拣
→ OCR=0 + 分组一次
→ smartSortStatus=completed + 可见 group membership
```

页面的“智拣/重新智拣”、重置按钮、照片状态徽标、“待智拣”和“待整理”筛选及数量统计统一读取同一个逐照片阶段分类结果。`sortStatus` 继续服务归档、预览和历史 OCR 兼容，不再承担“平台数据存在即智拣完成”的含义。自动快照保存 `smartSortStatus`；旧快照缺少该字段时按 `not_run` 安全恢复。completed 快照恢复时同时恢复 `smartSortResult` 和成员关系；重置快照恢复时保留平台基线且仍为待智拣。

### 局部智拣的照片级增量合并

单次智拣只处理当前选中且通过 eligibility 的照片。未选中照片的 `smartSortStatus`、三个 ByPhoto 映射、来源信息、人工状态和有效 group membership 均保持原值。局部结果按以下顺序合并：

```text
从旧 smartSortResult 移除本次目标照片的旧 membership
→ 删除空分组
→ 追加本次成功照片的新分组
→ 按 photoId 去除跨分组重复 membership
→ 重算每组 photoCount、总 groupCount 和总 photoCount
→ 从最终结果生成唯一 groupMembershipByPhotoId
```

本次处理失败的照片不保留旧 membership，并写入 `smartSortStatus=failed`；同批其他成功照片正常追加，未选中照片不受影响。`groupMembershipByPhotoId` 是照片徽标、待智拣筛选、待整理筛选、数量统计、分组视图和自动快照共同使用的成员事实来源。

逐照片阶段固定为：

```text
not_run / failed + 非特殊状态
→ 待智拣

completed / needs_completion
+ 存在于当前有效 groupMembershipByPhotoId
+ 尚未人工确认且非忽略、归档、原图缺失等特殊状态
→ 待整理
```

待智拣与待整理必须互斥，不得根据全局 `smartSortResult` 是否存在、旧 `sortStatus`、recognition、watermark 或 archive suggestion 是否存在推断。20 张全部待智拣时局部处理 6 张，结果固定为 membership 6、待整理 6、待智拣 14；已有 membership 15 后再处理另外 2 张，结果固定为 membership 17、待整理 17、待智拣 3。

### 智拣分组日期硬边界

智拣分组使用唯一的四维 `groupKey`，固定包含归一化日期、正式项目、归档分类和工作内容。日期是硬边界：后三项即使完全相同，只要日期不同就必须拆组；Marki 与本地照片来源不同不是拆组条件，四维值相同即可同组。

日期统一归一化为 `YYYY-MM-DD`，优先级为人工确认日期、来源感知 `effectiveResult.date`、可信 `watermarkRecord.captureDate`、当前有效 archive suggestion 日期、canonical 日期和来源可信拍摄时间。时间戳始终按固定 UTC+8 计算，不依赖运行电脑时区。缺失或非法日期不使用共同空值；每张照片以 `missing_date:<photoId>` 形成独立签名，并标记需要人工补充。

局部智拣先移除选中照片旧 membership，再根据全部成员当前 canonical 结果重建旧无日期分组，按新 `groupKey` 拆分或合并。只有四维签名完全一致才复用已有分组；同一照片只能保留一个 membership，空分组删除，未选中照片的有效 membership 保留。分组的 `suggestedFields.date`、左侧分组日期、组内成员 canonical 日期和右侧表单日期使用同一来源，禁止静默采用第一张照片日期。

自动验证新增 8 个真实行为场景，覆盖不同日期拆组、同日不同时刻合组、Marki 与本地跨来源分组、UTC+8 午夜边界、日期缺失隔离、旧无日期组重建、局部改期重分组、右侧表单一致性及完整 Marki OCR 为零且平台对象不变。该修复不改变 OCR、项目分类匹配、预览、归档或 Excel 规则。

### 智能分类到归档表单的单向数据闭环

“智能分类”后的权威数据流收口为：

```text
当前照片可信来源
→ watermarkTemplateType
→ sourceCanonical
→ effectiveArchiveInfo
→ 四维 groupKey
→ 叶子业务组
→ groupCanonical
→ 当前照片 form seed
→ 照片/组作用域人工草稿
→ 模板条件校验
→ 工作台快照
```

模板只由当前照片的 Marki 可信模板名、结构化字段、OCR 明确水印标题或明确字段标签组合判断。`archiveCategory`、组标题、组建议、上一张照片和右侧表单均不得反推模板。机动车模板只有可信模板名明确为机动车违规管理，或当前照片同时存在明确车牌与违停类型字段时成立；单个“车辆”“停车”或“秩序”词不成立。时间地点使用可信模板名或 OCR 明确“时间地点”标题，不能由分类值兜底。

`sourceCanonical` 仅由当前照片来源对象和当前启用配置精确匹配生成，不读取分组、全局表单或其他照片。`effectiveArchiveInfo` 只叠加当前照片已确认值和当前照片草稿。右侧表单只读取合法叶子组的共同字段、当前照片有效字段及各自作用域草稿；不得读取项目父标题、第一张成员、上一组表单或旧 suggestion 的随机组合。

四维键固定为日期、正式项目、正式归档分类和正式工作内容。缺失维度使用照片级隔离签名：

```text
missing_date:<photoId>
missing_project:<photoId>
missing_category:<photoId>
missing_work_content:<photoId>
```

时间地点的工作内容维度固定为 `not_applicable`。旧项目组、旧日期+项目组和其他与当前单张 canonical 不一致的 membership 在自动快照或手工草稿恢复时离线重建，不访问网络、不重新 OCR。旧组草稿只有在完整 `groupKey` 语义一致时迁移，错误混合组草稿不得复制到拆分后的组。

合法叶子组通过 `groupCanonical` 聚合日期、项目、分类、工作内容和模板。任一共同维度冲突时标记 `invalid_group`，不得采用第一张或多数值。车牌、施工单位、位置、备注和关键词属于照片级或可多值字段；差异记录为 mixed，不得覆盖其他成员。当前界面仍为扁平叶子组列表，没有把项目标题作为可编辑父节点。

时间地点模板在来源、canonical、effective、group descriptor、主进程分组结果、group canonical 和 form seed 中保持 `time_location`。现有 JSX 已由该模板值自然驱动：模板控件不显示，工作内容显示“不适用”且不进入缺失字段；没有增加基于“归档分类=时间地点水印”的截图特判。

本轮新增 P0 自动验证执行 118 个行为场景、111 个行为断言、6 个源码契约断言、10 个快照恢复断言和 3 个 Marki 零网络/零 OCR 断言。覆盖三类模板防污染、正式配置精确匹配、四个缺失维度照片级隔离、四维拆组、真实主进程分组服务、组/照片字段聚合（含空值冲突）、作用域草稿、旧混合组离线重建、快照往返和完整 Marki 来源对象不变。

### 马克查询筛选与导入生命周期

马克照片远程查询继续只提交团队、成员和 UTC+8 起止时间。当前开放接口不提供水印分类和本地导入状态筛选参数，因此页面在“当前已加载结果”上执行客户端筛选，不自动无限翻页。顶部同一查询条件卡片同时承载团队、成员、水印分类、导入状态、开始时间、结束时间和查询按钮；页面分别保存 `rawQueryResults` 与 `filteredQueryResults`，显示已加载、当前筛选和已选择数量。

水印身份只来自查询结果中的可信 `markName` 或结构化水印名称字段。当前真实响应和既有验证脚本没有稳定 `markId/templateId/mediaId`，因此第一版使用 NFKC、trim 和连续空白规范化后的名称作为筛选身份，不硬编码业务模板。默认筛选为“全部有水印”，另提供动态水印名称、“无水印”和“全部（含无水印）”。无水印照片只允许查看，选择框禁用，不能进入全选、下载清单、工作池、OCR 或智能分类；主进程恢复可信 moment 后再次校验水印身份，不能只依赖 renderer。

查询结果的安全生命周期状态为：

```text
discovered
filtered_unwatermarked
queued
downloading
downloaded
append_pending
imported_active
failed_retryable
removed_reimportable
archived_locked
```

`imported_active` 的权威依据是当前工作台快照仍存在相同 `sourceKey`；历史 manifest 的 `imported` 只表示本地 JPG 下载与校验完成，不能永久阻止重新导入。未完成 lifecycle 批次中的 queued/downloading/downloaded/append_pending 形成临时活跃占用；失败、撤销、取消和已清除历史记录本身不形成永久占用。当前 API 没有媒体级稳定 ID，`sourceKey` 继续兼容 `marki_api:<orgId>:<momentId>`；同一 sourceKey 同时出现无水印和有水印摘要时，可信会话保留有水印版本，避免无水印结果抢占。

主进程在 `userData/marki-import-lifecycle.json` 保存原子导入 ledger。批次状态固定为 created、downloading、ready_to_append、appending、completed、partial_failed、failed、cancelled 和 cleared；单项状态使用上述生命周期集合。ledger 只保存批次 ID、安全查询摘要、显示编号、水印名称、安全状态和失败 code/message，不保存 moment、URL、content、路径、KEY 或工作台包。

导入顺序固定为：恢复可信 token → 实时来源状态与筛选复核 → 原子占用 sourceKey → 创建 lifecycle 批次 → 最多三路下载并保持输入顺序 → 建立临时导入批次 → 结构化元数据 → ready_to_append → renderer 追加工作台 → 保存工作台快照 → appending → consume → imported_active/completed。下载或元数据失败保留已成功 JPG 和单文件元数据，只把失败项标记为 `failed_retryable`；原 token 集合内重试复验并复用成功缓存。

撤销导入先从工作台快照移除本批次尚未归档的照片、三个 ByPhoto 映射、照片草稿和失效 membership，保存新快照成功后才把 ledger 更新为 `removed_reimportable`。清除记录是软清除，不删除工作池照片、不释放活跃 sourceKey；存在未完成或可重试项目时禁止清除。安全缓存清理只删除不被工作池和未完成事务引用的 retryable 缓存，不改变来源状态或审计信息。

启动恢复不访问马克网络、不执行 OCR。工作台已存在 sourceKey 时补记 imported_active；下载中断或仅下载完成但未形成可追加批次时转为 failed_retryable；ready/appending 且尚未进入工作池的 append_pending 项恢复为 ready_to_append；已从工作池移除的 imported_active 记录转为 removed_reimportable。下载缓存复用前继续严格校验路径边界、普通 JPEG、大小、宽高和 SHA-256；撤销重导或失败重试由用户主动发起，缓存缺失或校验失败时才允许进入受控重新下载，损坏旧文件先隔离而不静默覆盖。

本节不修改智能分类、水印模板、canonical、业务分组、右侧表单、归档、Excel 或版本号。

## 11. 六阶段完整工作流重建

当前实现已将配置、照片实体、来源 canonical、智能分组、归档表单、预览计划、正式归档事务、台账追溯和导入运维收口到一条业务链：

```text
RuntimeConfiguration
→ 健康照片实体
→ 可信来源与 sourceCanonical
→ effectiveArchiveInfo
→ 四维业务分组
→ 模板驱动归档表单
→ 冻结 PreviewPlan
→ 原子 ArchiveTransaction
→ Excel 台账与来源追溯
→ 导入生命周期和故障恢复
```

系统配置只以 `userData` 中的 RuntimeConfiguration 为权威来源。照片来源目录和归档根目录由主进程注入；扫描统一执行文件存在、普通文件、格式结构、尺寸和 SHA-256 健康检查。工作台快照只保存工作状态和可离线恢复数据，不反向覆盖系统目录配置。

本地照片与 Marki 照片进入同一照片实体和工作池。本地来源固定为 `local_file`，Marki 来源固定为 `marki_api`。本地扫描采用追加和全池内容指纹去重；Marki 使用可信查询会话、selectionToken、来源清单、批次和 lifecycle ledger。完整 Marki 平台结构化信息直接进入 canonical，OCR 调用为零；缺失必要字段时 OCR 只形成补充层，不覆盖平台基线。

单张照片经模板识别、正式配置精确匹配和 canonical 解析后，使用日期、项目、归档分类和工作内容组成四维分组键。缺失维度使用照片级隔离键，时间地点水印使用 `not_applicable`。组级共同字段与照片级车牌、施工单位、位置、备注和关键词分离，草稿分别按组和照片保存，自动快照恢复时离线校验 membership。

归档预览不创建目录、目标文件、事务或台账。主进程生成严格白名单 `PreviewPlan`，冻结来源大小与 SHA-256、目标相对路径、归档字段和计划哈希。正式归档只接受完整且未被修改的计划；执行前重新校验来源和目标。预览后来源变化或目标被占用会使计划失效，不静默重命名。

正式归档在目标同目录写入唯一事务暂存文件，写入并同步后校验大小和 SHA-256，再通过独占硬链接原子安装到冻结目标。单项失败与其他照片隔离；成功照片继续进入台账。事务在磁盘保存 `planned/copying/copied/ledger_pending/committed/copy_failed/target_conflict` 阶段，重试复用同一事务和目标，进程重启可恢复完整暂存文件或待补记台账，不重复复制和追加。

Excel 台账保留原 11 个业务列，并增加来源类型、来源标识、照片 ID、来源文件路径、来源文件 SHA-256、归档文件 SHA-256、归档事务 ID、水印模板和识别处理方式。旧台账缺少新增列时补空读取，原业务列不迁移改义。新归档记录可从台账追溯到工作台照片、来源、处理模式和归档事务。

Marki lifecycle 支持失败重试、append/consume 半成功恢复、撤销导入、撤销后重导、软清除历史记录和安全缓存清理。撤销和清理不删除工作台之外的用户原始照片；已归档项保持锁定。缓存只在不被工作台或未完成任务引用时清理，活跃去重与历史记录分离。

所有自动验证均使用系统临时目录、模拟 API 和模拟图片，不访问真实 Marki 平台，不读取真实组织 KEY，不使用用户照片执行 OCR，也不修改真实来源目录、批次、缓存、归档文件或 Excel 台账。
